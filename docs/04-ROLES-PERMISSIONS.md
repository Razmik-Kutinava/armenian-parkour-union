# 04-ROLES-PERMISSIONS: Роли и права доступа

> Отвечает на вопросы: кто что может делать, какие данные кому видны, где и как проверяются права.
> Правила работы агента — `.cursor/rules/main.mdc`. Структура данных — только `02-DATABASE.md`. Бизнес-правила и условия — только `03-BUSINESS-RULES.md`.

Все проверки выполняются **на сервере**. Скрытие кнопки в интерфейсе защитой не считается.

**Для агента:**
- Проверка прав — опасная зона из правил: минимальный diff, тесты из раздела 8 обязательны.
- Нет действия в матрице — значит запрещено. Нужно новое право — стоп и вопрос, не добавлять самому.
- Новый код права добавляется одновременно в этот документ и в `permissions.ts`, только с согласия владельца.

## 1. Принципы
1. По умолчанию доступ закрыт. Разрешено только то, что явно перечислено ниже.
2. Роль задаёт доступ к админке (`users.role`). Степень, тренерский и судейский профиль доступ к админке **не дают**.
3. Участник работает только со своими данными. Чужие данные доступны только ролям из матрицы.
4. Каждое действие, которое меняет баллы, степени, сертификаты, платежи, роли, настройки, пишется в `audit_log`.
5. Права проверяются через единую функцию `can(user, permission)` (раздел 5), а не условиями «если роль == admin» в коде маршрутов.

## 2. Роли

| Роль (`user_role`) | Кто это | Доступ в админку |
|---|---|---|
| Гость | Не вошёл в систему | нет |
| `member` | Участник (включая тренеров и судей) | нет, только личный кабинет |
| `editor` | Ведёт контент: новости, страницы, события, главная, магазин (каталог) | да, раздел контента |
| `moderator` | Проверяет видео, согласия, экзамены, отмечает события, обрабатывает заказы | да, раздел модерации |
| `admin` | Полный доступ | да, всё |

Дополнительные признаки (не роли, но влияют на доступ):
- **Подтверждённый email** (`email_verified`)
- **Действующее членство** (есть `memberships.status = active`)
- **Статус** (`users.status = blocked` отнимает все права, кроме просмотра публичных страниц)
- **Возраст** (до 18 нужно согласие родителя для регистрации на события)
- **Профиль тренера или судьи** (`staff_profiles`): только публичный профиль и отметка, дополнительных прав в MVP нет

**Экзаменатор** в MVP это роль `moderator`. Он назначает экзамены и вносит результаты, сертификат выдаёт только `admin`.

Один пользователь имеет одну роль. Чтобы человек был и участником, и админом, он просто `admin`: личный кабинет у него тоже есть.

### 5.2 Где проверять
1. `hooks.server.ts` определяет пользователя по сессии и кладёт в `locals.user`. Заблокированного пользователя считает гостем.
2. Группа маршрутов `/admin/*`: общий `+layout.server.ts` пускает только `editor`, `moderator`, `admin`. Остальным 404.
3. Каждый раздел админки в своём `+page.server.ts` и в каждом form action повторно проверяет конкретное право: `requirePermission(locals.user, 'events.write')`. Проверки в layout недостаточно.
4. Меню админки показывает только разделы, доступные роли, но это только удобство.
5. API-маршруты и вебхуки: пользовательские проверяют сессию и право; вебхуки платежей проверяют подпись провайдера, сессии у них нет.
6. Сервисы (`services/`) принимают `actor` и сами проверяют право на операции, которые меняют баллы, степени, платежи. Так защита работает, даже если вызов придёт из другого места.

### 5.3 Проверка «своё»
Для кабинета каждая выборка и мутация фильтруется по `user_id = locals.user.id`. Идентификатор владельца берётся из сессии, а не из параметров запроса или формы.
Пример: `GET /cabinet/certificates/{id}` отдаёт запись только если `certificates.user_id = locals.user.id`, иначе 404.

### 5.4 Ответы на запрет
- Гость в закрытый раздел: переход на вход.
- Нет прав на существующий ресурс: 404 для чужих данных (чтобы не раскрывать, что они есть), 403 для известных разделов.
- Ошибки не показывают технических деталей.

## 6. Защитные правила
1. **Первый админ** создаётся seed-скриптом из переменных окружения. Других способов стать админом нет.
2. Роли назначает только `admin`. Нельзя менять роль самому себе.
3. В системе всегда должен остаться минимум один активный `admin`. Операция, которая это нарушает (понижение, блокировка, удаление последнего), отклоняется.
4. Админ не может заблокировать себя.
5. Модератор и редактор не могут просматривать и менять учётные записи с ролью выше или равной своей.
6. Смена роли, блокировка и ручные действия с баллами, степенью, сертификатами и платежами всегда пишутся в `audit_log` (кто, что, было и стало, IP).
7. Для входа с ролями `editor`, `moderator`, `admin` ограничение попыток входа строже, чем для участников (rate limit).
8. Сессии: срок жизни ограничен, смена пароля завершает остальные сессии, при блокировке пользователя сессии отзываются.
9. Рекомендация: двухфакторная защита для `admin` (включить после MVP).

## 7. Матрица «условие допуска» для действий участника

| Действие | Нужно |
|---|---|
| Оплата взноса | вход, подтверждённый email |
| Регистрация на событие | вход, подтверждённый email, активное членство, согласие родителя (до 18), подходящая категория |
| Добавление видео | вход, активное членство |
| Заказ в магазине | вход, подтверждённый email, хватает баллов, `status = active` |
| Подача на экзамен | вход, активное членство, подходящая степень (см. `03`, раздел 3) |
| Донат | ничего |

Сами условия (что считается «активным членством», «подходящей степенью») определяет `03-BUSINESS-RULES.md`; здесь — только кому и на что они нужны.

## 8. Что проверить тестами (минимум)
- Участник не видит чужие платежи, баллы и сертификаты (подмена `id` в URL).
- Редактор не может открыть платежи, баллы и пользователей даже по прямой ссылке и прямым запросом к action.
- Модератор не может начислить баллы и выдать сертификат.
- Последний админ не может понизить или заблокировать себя.
- Заблокированный пользователь теряет доступ сразу, а не после окончания сессии.
- Вебхук без подписи или с неверной подписью отклоняется.
