# 07-PAYMENTS: Платежи

> Отвечает на вопросы: как сайт принимает деньги, какие сценарии оплаты, как обрабатываются подтверждения, статусы, ошибки и возвраты.
> Правила работы агента — `.cursor/rules/main.mdc`. Структура данных — только `02-DATABASE.md` (`payments`, `payment_webhook_events`, `donation_purposes`). Логика — `03-BUSINESS-RULES.md`, раздел 10. Права — `04-ROLES-PERMISSIONS.md`.

Документ описывает поведение, а не код: он не зависит от языка и фреймворка. Где лежит код — по структуре из `01-STACK.md` (сервис платежей и модули провайдеров отдельно).

**Для агента:**
- Платежи — опасная зона из правил: минимальный diff, тесты из раздела 15 обязательны.
- Реальный провайдер не подключать, пока владелец не заполнил раздел 13. До этого — только провайдер `mock`.
- Поля, которых нет в `02-DATABASE.md` (см. раздел 17), — сначала правка схемы с согласия владельца.

## 1. Принципы

1. **Провайдер не выбран.** Код пишется под единый контракт провайдера (раздел 4). Конкретный провайдер подключается отдельным модулем и не влияет на остальной код.
2. **Карточные данные никогда не попадают на наш сервер.** Оплата только на странице провайдера (редирект) или в его встроенной форме. Мы храним только ID платежа и статус.
3. **Редиректу не доверяем.** Возврат пользователя на `/payment/success` ничего не подтверждает. Статус `paid` ставится только после подтверждения от провайдера: подписанный вебхук (callback) или прямой запрос статуса к API провайдера (раздел 7).
4. **Деньги в минимальных единицах** (`amount_minor`, целое) плюс `currency`. Сумма и валюта в подтверждении провайдера должны совпадать с нашей записью.
5. **Идемпотентность.** Одно и то же подтверждение, пришедшее дважды, обрабатывается один раз.
6. **Три типа платежей** (`payment_kind`): `membership`, `donation`, `event_fee`. Разные сценарии, разные отчёты, не смешиваются.
7. **Побочные эффекты в данных** (членство, регистрация, баллы) выполняет сервис платежей в одной транзакции вместе со сменой статуса. Письма и PDF — после успешного коммита (`03`, раздел 14).
8. **Ручное подтверждение** (`provider = manual`) всегда доступно админу как запасной путь.

## 2. Выбор провайдера (решение владельца)

Для Армении основные кандидаты:

| Вариант | Что это | Заметки |
|---|---|---|
| Банковский эквайринг (например vPOS Ameriabank) | Карты Visa, Mastercard, ArCa | Нужен договор с банком. Валюты и возвраты зависят от условий банка |
| Idram | Кошелёк и оплата через него | Часто подключают вместе с банковским шлюзом |
| Telcell | Кошелёк | Опционально |
| Агрегатор ArCa | Единая интеграция для нескольких банков | Проверить, подходит ли для НКО и какие комиссии |
| Зарубежный шлюз (Stripe и др.) | Через иностранное юрлицо | Не для MVP: меняет юридическую и налоговую схему |

**Что выяснить у банка или провайдера до начала интеграции** (результат записать в раздел 13):
1. Подключают ли НКО, какие документы нужны, сроки подключения.
2. Комиссия за приём платежа, за возврат, ежемесячные платежи.
3. Поддерживаемые валюты (AMD, USD, EUR) и нужны ли отдельные счета под каждую.
4. Есть ли тестовая среда (sandbox) и тестовые карты.
5. Как провайдер подтверждает платёж: подписанный вебхук, callback без подписи или нужно запрашивать статус самим.
6. Как делаются возвраты (через API или вручную в кабинете банка).
7. Есть ли оплата на странице провайдера с нашим дизайном, поддержка армянского и русского языков.
8. Требования к договору оферты, политике возвратов и реквизитам на сайте.
9. Налоговые и отчётные особенности для НКО (уточнить у бухгалтера федерации).

Рекомендация для MVP: один банковский эквайринг для карт, Idram вторым этапом.

## 3. Общая схема платежа

```
Пользователь → [Сервис платежей: создать платёж pending] → [Провайдер: создать сессию оплаты]
            → редирект на страницу провайдера → оплата
            → провайдер подтверждает (вебхук / проверка статуса)
            → [Сервис платежей: paid + побочные эффекты] → письмо
Пользователь возвращается на /payment/success и видит актуальный статус из нашей БД
```

Шаги:
1. Пользователь жмёт «Оплатить». Сервер **сам** определяет сумму (взнос из `site_settings.membership_fee`, цена события из `events`, сумма доната из формы после валидации). Сумма с клиента для взноса и события не принимается.
2. Создаётся запись `payments` со статусом `pending` и сроком ожидания оплаты.
3. Сервер просит провайдера создать сессию оплаты, получает ID платежа у провайдера и адрес страницы оплаты, сохраняет ID.
4. Пользователь переходит на страницу оплаты.
5. Подтверждение приходит по разделу 6 или 7.
6. После подтверждения платёж становится `paid` и запускаются побочные эффекты (раздел 5).
7. Страница `/payment/success` показывает статус из БД. Если платёж ещё `pending`, показывается «Проверяем платёж...» и страница несколько раз опрашивает статус, затем сообщение «Платёж обрабатывается, мы отправим письмо».

## 4. Контракт провайдера

Каждый провайдер — отдельный модуль с одинаковым набором операций. Остальной код работает только через этот контракт и не знает, какой банк подключён.

**Описание провайдера:** идентификатор (`ameriabank`, `idram`, `manual`, `mock`) и список поддерживаемых валют.

| Операция | Получает | Возвращает | Обязательна |
|---|---|---|---|
| Создать оплату | наш ID платежа, сумму в минимальных единицах, валюту, описание, адрес возврата при успехе и при отмене, язык страницы (`ru`/`hy`/`en`), email плательщика (необязательно) | ID платежа у провайдера, адрес страницы оплаты, сырой ответ | да |
| Разобрать уведомление (вебхук) | входящий запрос как есть | ID события (для дедупликации), ID платежа у провайдера, статус (`paid`/`failed`/`cancelled`/`refunded`), сумму, валюту, сырые данные — или «не распознано». **Обязана проверить подпись**, если провайдер её даёт | если провайдер шлёт вебхуки |
| Узнать статус | ID платежа у провайдера | статус (`pending`/`paid`/`failed`/`cancelled`/`refunded`), сумму, валюту, сырой ответ | да |
| Вернуть деньги | ID платежа у провайдера, сумму (в MVP только полную), причину | успех или ошибка, сырой ответ | если провайдер поддерживает возврат через API |

Правила:
- Есть единый реестр провайдеров. Провайдер включается переменной окружения и `feature_flags`.
- Провайдер `mock` существует только в `development`: имитирует оплату и вебхуки, чтобы всю цепочку можно было проверить без банка.
- Провайдер `manual` не создаёт редирект: платёж создаётся админом из админки сразу в статусе `paid` (раздел 9).
- Если у провайдера нет вебхуков, подтверждение идёт только через «Узнать статус» (раздел 7).

## 5. Сценарии по типам платежей

### 5.1 Членский взнос (`membership`)
1. Условия: вход, подтверждённый email (`04`, раздел 7).
2. Сумма: `site_settings.membership_fee` (сумма, валюта, срок).
3. До оплаты: создаётся `memberships` со статусом `pending` и ссылкой на платёж. Прав не даёт.
4. После `paid` (транзакция): членство `active` с периодом по `03`, раздел 2; если `users.level` пуст, ставится `novice`. Письмо об оплате — после коммита.
5. Если платёж `failed` или `cancelled`: запись `memberships` остаётся `pending` и закрывается (`cancelled`) при истечении платежа.
6. Повторное нажатие «Оплатить» при существующем `pending` платеже: переиспользуется незавершённый платёж, пока не истёк срок ожидания; иначе создаётся новый.
7. Возврат: `03`, раздел 2, пункт 6.

### 5.2 Донат (`donation`)
1. Доступен без входа. Поля: сумма (минимум и максимум задаются в `site_settings`), валюта, назначение (`donation_purposes`), имя и email (для гостя), `is_anonymous`.
2. Сумму вводит пользователь, поэтому проверка диапазона обязательна на сервере.
3. После `paid`: статус сохраняется, письмо-благодарность на email донора с квитанцией. Баллов и степени донат не даёт.
4. У вошедшего пользователя платёж привязывается к `user_id`, у гостя `user_id = null` и заполнены `donor_name`, `donor_email`.
5. Разовые донаты. Регулярные (подписки) не входят в MVP.

### 5.3 Участие в событии (`event_fee`)
1. Применяется для событий с `price_amount_minor > 0`.
2. Порядок: пользователь регистрируется (`03`, раздел 7) → создаётся регистрация в ожидании оплаты и платёж `pending` со сроком (удержание места, значение из настроек) → оплата.
3. После `paid` (транзакция): регистрация становится активной (`registered`), начисляются баллы за регистрацию. Письмо — после коммита.
4. Если платёж не завершён до конца срока: платёж `cancelled`, регистрация отменяется, место освобождается, первый из очереди получает предложение (`03`, раздел 7, пункты 3 и 4).
5. Если оплата пришла **после** истечения удержания: сервис проверяет, есть ли свободное место. Есть — регистрация активируется. Нет — платёж помечается `paid`, регистрация не активируется, админу уходит задача «вернуть деньги или найти место» (раздел 8).
6. Отмена регистрации участником и возврат: решает админ (`03`, раздел 7, пункт 5).

### 5.4 Покупки в магазине
Магазин работает **только за баллы**. Денежной оплаты нет (`03`, раздел 9).

## 6. Вебхуки и callback

1. Маршрут: `POST /api/webhooks/{provider}`. Без сессии, защита подписью провайдера.
2. Порядок обработки:
   1. Принять запрос, прочитать тело как есть (для проверки подписи).
   2. Провайдер разбирает уведомление и проверяет подпись. Неверная подпись или формат: ответ `400`, запись в лог, ничего не меняем.
   3. Записать событие в `payment_webhook_events` с ограничением `unique(provider, event_id)`. Дубликат: ответить `200` и ничего не делать.
   4. Найти платёж по `provider_payment_id`. Не найден: записать ошибку в событие, ответ `200` (чтобы провайдер не повторял бесконечно), админу уведомление.
   5. Сверить сумму и валюту. Расхождение: платёж в `failed` с причиной `amount_mismatch`, флаг «требует проверки», уведомление админу, побочные эффекты не запускаются.
   6. Применить переход статуса по таблице (раздел 10). Недопустимый переход игнорируется и логируется.
   7. Для `paid` выполнить побочные эффекты (раздел 5) в **одной транзакции** со сменой статуса.
   8. Отметить `payment_webhook_events.processed_at`.
3. Ответ провайдеру: `200` после успешной записи события, даже если бизнес-обработка отложена. Тяжёлые действия (письма, PDF) не должны задерживать ответ.
4. Если обработка упала после записи события: `error` заполняется, ответ `500`, чтобы провайдер повторил. Повтор безопасен благодаря идемпотентности.
5. Порядок событий не гарантирован: платёж `refunded` не должен быть перезаписан поздним `paid`. Переходы только по таблице статусов.
6. Локальная разработка: вебхуки проверяются через туннель (например cloudflared) или провайдером `mock`.

## 7. Проверка статуса и сверка (если вебхуков нет или они потерялись)

Многие банки не присылают подписанный вебхук, а ждут, что мы сами спросим результат. Поэтому есть второй путь подтверждения.

1. **Страница возврата** `/payment/success?pid=...`: сервер спрашивает статус у провайдера и, если провайдер подтвердил `paid`, применяет тот же сервисный путь, что и вебхук (с той же идемпотентностью).
2. **Фоновая сверка** каждые 5 минут: все платежи `pending` старше 2 минут и не старше суток проверяются у провайдера. Результат применяется так же.
3. **Истечение:** платёж `pending` с истёкшим сроком после проверки у провайдера (не оплачен) переводится в `cancelled`, запускаются последствия (освобождение места, закрытие членства `pending`).
4. **Ежедневная сверка** с отчётом банка: админ загружает или смотрит выписку; расхождения (оплата в банке есть, у нас нет и наоборот) попадают в список «Требуют проверки» в админке.
5. Все автоматические переходы пишутся в `audit_log` с `actor = null`.

## 8. Нештатные ситуации

| Ситуация | Что делает система |
|---|---|
| Провайдер не отвечает при создании оплаты | Платёж `failed`, пользователю «Не удалось начать оплату, попробуйте позже», запись в лог, повтор вручную |
| Пользователь закрыл страницу оплаты | Платёж остаётся `pending`, сверка (раздел 7) подтвердит или закроет |
| Деньги списаны, на сайте `pending` | Сверка у провайдера; если не помогает, админ подтверждает вручную по выписке |
| Сумма в подтверждении не совпала | `failed` + «требует проверки», автоматические эффекты не запускаются |
| Подтверждение для неизвестного платежа | Запись в `payment_webhook_events`, уведомление админу |
| Оплата пришла после снятия места на событие | Раздел 5.3, пункт 5 |
| Платёж подтверждён, но транзакция побочных эффектов упала | Откат, повтор при следующей сверке или вебхуке, платёж остаётся `pending` |
| Двойное нажатие «Оплатить» | Один активный `pending` платёж на сценарий; кнопка блокируется при отправке |
| Двойная оплата одного и того же | Второй платёж `paid` помечается «требует проверки», админ оформляет возврат |
| Пользователь заблокирован, пока платёж в обработке | Платёж проходит, членство и регистрации не активируются, «требует проверки» |

## 9. Ручные платежи (админ)

Для переводов вне сайта (банковский перевод, наличные на событии):
1. В админке «Платежи» → «Подтвердить вручную» (`05-ADMIN-PANEL.md`, раздел 16).
2. Поля: плательщик (участник или гость), тип, сумма, валюта, дата, комментарий (например номер платёжки).
3. Создаётся `payments` с `provider = manual`, `status = paid`, `confirmed_by = админ`. Побочные эффекты запускаются теми же сервисами, что при онлайн-платеже.
4. Запись в `audit_log` обязательна.

## 10. Статусы и переходы

Статусы (`payment_status`): `pending`, `paid`, `failed`, `cancelled`, `refunded`.

| Из → В | Кто или что инициирует |
|---|---|
| `pending` → `paid` | подтверждение провайдера (вебхук, проверка статуса) или админ (ручной) |
| `pending` → `failed` | ошибка провайдера, расхождение суммы, отказ банка |
| `pending` → `cancelled` | истёк срок ожидания или отмена пользователем |
| `paid` → `refunded` | админ (возврат) или подтверждение возврата от провайдера |
| `failed` → `paid` | допускается, если провайдер позже подтверждает оплату и сумма совпадает |
| `cancelled` → `paid` | допускается так же, при поздней оплате (раздел 5.3, пункт 5) |

Остальные переходы запрещены. `paid` нельзя удалить и изменить сумму. `refunded` конечный статус.
Частичные возвраты в MVP не поддерживаются (только полный).

## 11. Возвраты

1. Возврат делает только `admin` (`04`, раздел 3.2), причина обязательна, запись в `audit_log`.
2. Если провайдер поддерживает возврат через API, вызывается операция «Вернуть деньги». Если нет, админ делает возврат в кабинете банка, затем отмечает в админке «Возврат выполнен» (статус `refunded`, `refunded_at`).
3. Побочные эффекты возврата:
   - **Взнос:** членство `cancelled`; степень и сертификаты не отзываются автоматически (`03`, раздел 2).
   - **Участие в событии:** регистрация `cancelled`, место освобождается; баллы за регистрацию снимаются обратной записью (`03`, раздел 6.2, пункт 6).
   - **Донат:** только статус, письмо донору.
4. Участнику уходит письмо о возврате.
5. Сроки зачисления денег зависят от банка и показываются в письме.

## 12. Квитанции, налоги и документы

1. После `paid` на email уходит письмо с квитанцией (сумма, дата, назначение, номер платежа, реквизиты федерации из `site_settings.requisites`). Копия доступна в `/cabinet/payments`.
2. Публичная оферта и политика возвратов: страницы `pages` (`offer`, `refund-policy`), ссылки в подвале и рядом с кнопкой оплаты, чекбокс согласия перед оплатой.
3. Налоговый и бухгалтерский учёт (НДС, статус НКО, оформление пожертвований) решается с бухгалтером федерации. **В код ничего не зашивается**; при необходимости добавляются поля или настройки.
4. Выгрузка CSV для бухгалтерии: взносы и донаты отдельными файлами по периоду (`05-ADMIN-PANEL.md`, раздел 16).

## 14. Безопасность

1. Секреты провайдера (логин, пароль, ключи) только в переменных окружения, не в БД и не в коде. Переменные группируются префиксом `PAYMENT_{PROVIDER}_*`, список ведётся в `.env.example` (`01-STACK.md`).
2. Данные карт нигде не хранятся и не логируются. В `provider_payload` сохраняется ответ провайдера **без** чувствительных полей (очищать перед записью).
3. Вебхуки: проверка подписи, дедупликация, проверка суммы и валюты, ограничение частоты запросов.
4. Тестовые и боевые ключи разделены окружениями. Боевой провайдер не может быть включён в `development`.
5. Сумма взноса и события определяется на сервере. Данные от клиента (сумма, ID платежа) не доверенные.
6. Все ручные операции с платежами и смена статуса пишутся в `audit_log`.
7. Для оплаты используется HTTPS, URL возврата и вебхуков строятся из `PUBLIC_SITE_URL`.

## 15. Что проверить тестами (минимум)

- Дубль вебхука не создаёт повторного членства и баллов.
- Вебхук с неверной подписью отклоняется и ничего не меняет.
- Несовпадение суммы или валюты не активирует платёж.
- Поздняя оплата события при отсутствии мест не ломает лимит.
- `pending` платёж после истечения срока закрывается сверкой и освобождает место.
- Донат без входа создаётся и подтверждается.
- Возврат корректно отменяет членство и регистрацию.
- Поддельный переход на `/payment/success` без подтверждения от провайдера не даёт `paid`.
- Ручное подтверждение админом запускает те же эффекты, что онлайн-платёж.

## 16. Порядок реализации

1. Сервис платежей, контракт провайдера, провайдер `mock`, переходы статусов, идемпотентность.
2. Взнос (`membership`) со всей цепочкой и письмом.
3. Донат, события (`event_fee`).
4. Фоновая сверка и истечение платежей.
5. Подключение реального провайдера (после выбора и получения доступов).
6. Возвраты и выгрузки CSV.
7. Второй провайдер (Idram) при необходимости.
