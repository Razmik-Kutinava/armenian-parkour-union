# 01-STACK: Технологии и структура проекта

> Отвечает на вопросы: какой стек, где что лежит, как слои связаны, какие команды и переменные.
> Правила работы агента — `.cursor/rules/main.mdc`. Структура таблиц — только в `02-DATABASE.md`.
>
> **Статус: предварительно.** Структура папок может меняться. Меняет её только владелец; агент предлагает изменение и ждёт «go», а не переделывает сам.

## Принципы
- Один монолит на SvelteKit: публичный сайт, личный кабинет, админка и API в одном приложении.
- Минимум зависимостей. Новую библиотеку добавлять только по согласованию (см. «Нельзя» в правилах).
- Всё строго типизировано (TypeScript strict).
- Версии фиксируются в `package.json` и lock-файле. Использовать актуальные стабильные версии на момент установки, не менять мажорные версии без просьбы.

## Хостинг и деплой
- **Приложение:** Fly.io, Docker-образ (`Dockerfile` + `fly.toml`), адаптер `@sveltejs/adapter-node`. HTTPS и сертификат даёт Fly, свой прокси не нужен. Регион — ближайший к Армении (предварительно `fra`).
- **База:** PostgreSQL в Neon (бесплатный тариф, регион Frankfurt). Один проект Neon, в нём две базы: `parkour_dev` (разработка) и `parkour_prod` (сайт). Это базы данных, не ветки git. Бэкапы — встроенные в Neon (несколько дней на бесплатном тарифе) плюс регулярный `pg_dump` с копией вне Neon.
- **Файлы:** Cloudflare R2, не на диске сервера.
- **Домен:** `parkour.am` (куплен), DNS указывает на Fly. Все ссылки и письма используют `PUBLIC_SITE_URL`.
- **Окружения:** `development` (локально, база `parkour_dev` в Neon), `production` (Fly + `parkour_prod`). CI поднимает свой временный Postgres. Отдельный `staging` по желанию позже.
- **Деплой:** `fly deploy` (из CI или локально), миграции запускаются перед стартом новой версии (`release_command`). Деплой — только по апруву владельца (`/deploy`).
- **Мониторинг:** Sentry — подключается после первого деплоя.

### Где хранятся секреты
| Где | Что |
|---|---|
| Fly (`fly secrets set`) | все боевые секреты приложения; зашифрованы, приходят в приложение как переменные окружения |
| GitHub Secrets | только `FLY_API_TOKEN` (deploy-токен на одно приложение) для деплоя из CI |
| Локально | `.env` (в `.gitignore`); шаблон без значений — `.env.example` |
| Менеджер паролей владельца (Bitwarden / 1Password) | главная копия всех ключей; доступ только у владельца |

В коде, в git и в БД секретов нет.

Новые папки верхнего уровня и новые разделы в `src/lib/server/` — только по согласованию. Без свалок `utils/`, `misc/`, `helpers/` без домена.

## Как слои связаны
- Маршрут (`+page.server.ts`, form action) принимает запрос, проверяет права, валидирует через Zod и вызывает **сервис**.
- Сервис содержит бизнес-логику и работает с БД через Drizzle. Маршруты не пишут логику начисления баллов или смены степени сами.
- Любое изменение баллов, степеней, платежей и ролей сервис пишет в `audit_log`.
- Админка и публичный сайт используют одни и те же сервисы.
- Права проверяются на сервере в каждом маршруте и в `hooks.server.ts` для `admin/`; скрытие кнопки в интерфейсе — не защита.

## Команды
| Команда | Что делает |
|---|---|
| `npm install` | Установка зависимостей |
| `npm run dev` | Локальный запуск |
| `npm run build` | Сборка |
| `npm run preview` | Проверка сборки |
| `npm run check` | Проверка типов (`svelte-check`) |
| `npm run lint` | ESLint и Prettier |
| `npm run test` | Тесты Vitest |
| `npm run test:e2e` | Тесты Playwright |
| `npm run db:generate` | Создать миграцию из изменений схемы |
| `npm run db:migrate` | Применить миграции |

Локально приложение подключается к базе `parkour_dev` в Neon (`DATABASE_URL` в `.env`). Docker не обязателен; если он есть, можно поднять Postgres через `docker compose up -d`.

**Проверка перед коммитом** (для отчёта «Проверка» из правил): `npm run check`, `npm run lint`, `npm run test`; для баллов, платежей и прав — плюс тесты этой зоны.

## Соглашения
- Схема БД лежит в `src/lib/server/db/schema/`, по одному файлу на группу сущностей. Источник правды по структуре: `02-DATABASE.md`.
- Миграции создаются только командой `db:generate`, руками не правятся. Перед `db:generate` и `db:migrate` — Migration Gate из правил (план + откат + «go»).
- Серверный код только в `src/lib/server/` и `+*.server.ts`.
- Unit-тесты Vitest лежат рядом с кодом: `points.ts` → `points.test.ts`.
- Загрузка файлов: клиент получает подписанную ссылку от сервера и грузит в R2 напрямую, сервер сохраняет только путь.
- Ошибки пользователю показываются понятным текстом, технические детали идут в лог.
- Размер файлов — по лимитам из правил (цель ≤ 50 строк, > 200 — сначала план сплита).

7. **Перетаскивание и очистка HTML** в админке (`05`): нужны ли отдельные библиотеки — решить до этапа 2.
8. **Языковой префикс в маршрутах:** решено — английский без префикса, `/hy/...` и `/ru/...` (`06`, раздел 1). Способ (например, параметр `[[lang]]`) — на этапе 1.
